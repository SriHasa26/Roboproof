# Seed blocks and scenario sets

## Seed blocks (`backend/app/core/seeds.py`)

| Block | Range | Used for | Rules |
|---|---|---|---|
| dev | 1,000 to 99,999 | sweeps, ceiling search, trap search, baselines, analysis sets, tests | may be reused freely. So far: 1000-1299, 3000-3023, 50000-50299 |
| rehearsal | 800,000 to 899,999 | end-to-end gate rehearsals | no dev sweep uses it; each run allocates a **fresh** sub-block from the ledger, never reused |
| held-out | 900,000 and up | official verification (gate G5) only | protected by `check_seed` (needs `held_out=True`); each sub-block can be used **once, ever** |

`held_out=True` is reachable only from `app/gate/`. Tests (`test_seed_guard.py`, `test_ledger.py`) statically scan `backend/app` and `scripts/` and fail if any other module passes the flag or names the held-out block in a ledger call.

## Seed ledger (`seed_ledger` table, `store/ledger.py`)

Every use of a seed block by a run is recorded: run id, block name, start, count, purpose, rehearsal flag, timestamp. For rehearsal and held-out blocks `allocate()` hands out the next free sub-block (sequential, never overlapping) and `record_use()` raises `SeedBlockReusedError` on any overlap with an earlier use. A failed official run therefore cannot be retried on the same held-out seeds; a new run gets a fresh block.

## Two kinds of scenario set

| | Analysis set | Verification set |
|---|---|---|
| Purpose | baseline, evidence, analyst, fixer, gate checks G1 to G4 | gate check G5 only |
| Built by | `ScenarioGenerator`: about 60% Latin-hypercube coverage + about 40% samples from regions proposed by the fast model (or the labelled fixture) | `gate/verification.py`: Latin-hypercube coverage of the frozen ranges, **no LLM, no model-proposed regions** |
| Seeds | dev block | rehearsal block (rehearsals) or held-out block (official runs), allocated by the ledger |
| Seen by analyst / fixer | yes | **never**. The fixer receives dev-stage feedback only (G1 to G4, G6); G5 is terminal |
| Sampler | Latin hypercube + risk-weighted regions | Latin hypercube, the **same sampler as the ceiling search and dev sweeps** |

**Why the verification set is a plain broad sweep:** the 0.90 held-out target was calibrated on broad Latin-hypercube sweeps (default policy about 72%, best-found about 97%). The generator's risk-weighted mix is harder: the 200-scenario baseline passed 66%, versus 72% on broad sweeps. Verifying on the risk-weighted mix would silently move the bar. The verification set is also generated by code alone so a model can never influence it.
